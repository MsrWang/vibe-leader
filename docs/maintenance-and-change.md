# 质量、Skill 维护与变更影响

本页补充[日常项目用法](project-workflow.md)，说明怎样选择修改位置、检查效果，以及在需求变化时控制遗漏。它随 3.0 有限范围交付；下面引用的案例只支持各自版本和场景，不证明新请求在所有任务中都有效。

## 先确定值得处理的具体问题

质量检查从当前目标和用户能感受到的影响出发。错误结果、已有文件被破坏、难以诊断的失败，应说明触发方式和受影响入口；维护成本问题应指出真实的重复修改或依赖牵连；性能问题需要可比较的场景与测量。

形成建议时，把问题位置、直接证据、影响、优先级、改法和验证方式放在一起。检查范围以当前目标为界，发现关联证据后再扩大；不凭局部检查给出全库正常的结论。具体问题没有成立时，可以交付保留现状的理由。

## 按原因选择修改位置

| 观察到什么 | 先核对什么 | 通常应怎样处理 |
|---|---|---|
| 程序返回异常或结果错误 | 输入、调用链、共用函数与已有输出 | 复现具体错误，修正实际根因并核对相关入口 |
| 规则没有涵盖必要行为，或要求相互冲突 | 当前适用规则、用户目标与对应失败表现 | 比较最小规则修订，用受影响场景验证改善与回归 |
| 正确规则已经存在，但实际没有落实 | 是否加载了适用内容，行动与计划如何选择 | 先修正执行或使用方式；不机械追加相同规则 |
| Skill 没找到、被禁用或来源不符 | 当前宿主发现结果与精确来源 | 处理对应调用问题；不拿同名文件代替正确来源 |
| 目标环境不支持某种操作 | 实际能力和可用替代方式 | 选择有依据的适配方法，保留支持范围 |

### 已完成案例：把编码错误处理放回共用读取层

库存工具和 Skill 选择工具使用同一组读取函数。维护前，一个入口处理了无效编码，另一个入口会出现未处理异常。根因位于共用读取层，所以修复放在那里，并去掉调用方的重复处理。

对应实现是 [`load_policy`、`read_response`](../workbench/skill_inventory.py) 和[选择入口](../workbench/skill_route.py)。[异常输入回归](../tests/test_skill_input_errors.py)覆盖两个入口、两类输入，以及输出尚不存在和已经存在的情况。该修复的相关验证确认错误输入不会创建新报告或破坏已有报告；它没有修改 Skill 规则，也没有证明真实宿主发现或所有环境均正常。交付范围见[2.3.1 说明](release-2.3.1.md)。

### 当前案例：阶段完成后遗漏整体下一项

某次维护发布后，主管说明了局部成果，却把整体后续普遍转成“等真实问题再触发”。用户因此需要再次提醒仍有计划未做。现有[工作流](../skill/vibe-project-lead-zh/references/manager-workflow.md)与[交付指引](../skill/vibe-project-lead-zh/references/human-delivery.md)已经要求保留原始目标和剩余成果。

仅凭这一次遗漏，还不能断言模型遗忘了上下文或规则必须重写。因此最初先把它记录为执行与计划接续遗漏：核对有效决定，恢复具体下一项并实际推进，再在后续检查点检查效果。这样避免把一次执行偏差直接扩大成规则缺陷。

用户随后又明确反馈，同一窗口每隔几分钟就结束一次，需要反复发送“继续”。结合实际轨迹检查后，问题被缩小为一处规则歧义：顶层主循环强调“一个下一安全步骤”，详细工作流要求只在有意义检查点更新，但没有直接说明“一个下一安全步骤不等于一个回合”。这时才具备了最小规则修订的依据。

修订只在主循环补充连续推进条件，并在[日常项目用法](project-workflow.md)说明用户可观察到的结果；没有增加第二套执行机制。相关合同先记录旧文字缺失的失败，再验证新文字和现有合同；完整回归与静态安全检查通过后，候选按独立预检、切换能力证明和实际升级三个边界处理。[3.0.1 说明](release-3.0.1.md)显示实际安装已经完成，旧版本和升级日志均已保留。

这条证据链证明问题分类、源码候选、验证和安装已经走通；当前窗口是否重新加载新版仍未验证，长期体验也不能由测试代填。当前任务继续推进，未来自然开启的新任务只补充加载与行为证据，不成为当前工作的前置条件。

## Skill 源码维护与实际生效分别处理

先确定当前项目究竟维护哪份源码、谁提供它，以及宿主实际加载哪份安装。以本项目为例，可维护源码是 [`skill/vibe-project-lead-zh/`](../skill/vibe-project-lead-zh/SKILL.md)；源码修订不会自动更新正在使用的安装。

在已委托的项目目标和范围内，调查、局部修复与候选准备可以连续进行。需要规则修订时，保留实际失败表现，提出最小改动，使用 writing-skills 验证对应行为，并检查原有场景是否受影响。旧版本在其他情境中的成功不能证明新规则有效；同一条规则已经足够时，应说明复用依据。

规则修订还涉及当次使用的辅助 Skill。核对 writing-skills 的当前来源、正文和必需依赖；例如本次读取的版本要求先理解 test-driven-development。主管自身文件没有变化，只能说明这一部分未变，不能据此推断辅助 Skill 或维护场景已经验证。前后的比较应覆盖本次实际使用的材料和同一个问题；不必重做无关场景。

涉及角色职责、适用场景、重要用户参与方式或权限时，先解释变化和取舍。安装候选前再核对当前版本、来源和恢复路径；具体步骤见[安装与恢复指南](getting-started.md)。若要恢复，先确认后续修改与真实安装状态，避免用旧副本覆盖新工作。其他项目或第三方插件的维护范围需要单独确定。

### 已有选择工具能帮助判断到哪一步

对保存的发现结果，源码中的[选择工具](../workbench/skill_route.py)可以核对本次选中的条目；操作入口见[2.3.1 使用说明](release-2.3.1.md)。它不运行真实发现，也不加载指令供模型执行。下面是当前实现的结果含义，可帮助维护者先判断调用问题，而不是直接重写 Skill。

| 结果或原因 | 当前含义 | 下一步 |
|---|---|---|
| `BLOCKED_SUPERVISOR` | 中文主管自身缺失、禁用、重复或不能校验 | 先查主管的正确来源和状态，停止依赖它的流程 |
| `BLOCKED_ROUTE` | 当前准备使用的其他 Skill 有问题 | 处理该选定能力的问题；不能推断所有能力都不可用 |
| `DISABLED`、`DUPLICATE`、`LOAD_ERROR` | 分别是禁用、同一发现标识重复和已归属的加载错误 | 查对应条目的状态与来源；需要变更安装或配置时单独处理 |
| `LOCATOR_CHANGED` | 提供了预期路径，且实际发现路径与它不同 | 先核对新来源，不能自行改成相信新路径；未提供预期路径时不具有这项前后比较结论 |
| `LOCATOR_UNVERIFIED` | 选定文件不能安全读取，或其声明身份无法匹配 | 查文件与发现身份；这个合并原因不能直接当作某一个具体根因 |
| `UNKNOWN` | 输入无法解析或校验，或加载错误无法归属 | 先补齐可判定信息，不能当作已确认是规则问题 |
| `VERIFIED` | 在本次提供的数据及本地文件范围内，选定身份校验通过 | 继续核对发现资料是否适用，并按实际任务加载、使用；这不表示完整库存、时效、指令执行或写入权限均已通过 |

未选中的条目存在可归属异常时，可作为旁支发现列出；它本身不一定阻断当前选择。无法归属的错误不能按无关问题忽略。相关实现与已有覆盖见 [`assess_skill_route`](../workbench/skill_inventory.py) 和[选择测试](../tests/test_skill_route.py)。这份说明来自当前源码核对，没有重新执行真实宿主发现或安装操作。

## 需求变化时，决定哪些检查仍然有用

变化开始时，说明用户现在要得到的结果，再沿真实依赖判断受影响的代码、数据、说明、使用步骤和环境。将旧证据分为仍适用、需要补验、尚不能判断三种情况；不要仅按文件数量或改动行数决定验证范围。

报告阅读修订提供了一个已有实例：详情无法展开后，全部展开又使页面难读，因此改成简明首页加独立详情页。这个变化的影响如下。

| 变化涉及的部分 | 需要核对的结果 | 证据边界 |
|---|---|---|
| 报告输出接口 | 两页输出可用，既有完整单页接口仍可使用 | 核对[报告实现](../workbench/progress_view.py)及其相关检查 |
| 保存与使用步骤 | 两份文件放在同一目录，往返链接正确，已有结果受保护 | 使用实际文档入口检查；仅有函数返回不证明文件可读 |
| 完成与安全语义 | 输入、结构化结果、完成判断与文本处理符合原合同 | 按相关实现是否变化判断哪些旧证据仍适用 |
| 阅读体验 | 当前阅读器中首页清楚、详情链接可用 | 已有代表用户反馈；不外推所有阅读器 |
| Skill 安装 | 工具变化是否涉及实际安装内容 | 本次 11 个 Skill 文件未变，因此没有由该改动产生的重装需要 |

这些事实支持本次报告变更的处理方法。涉及数据格式、迁移、多功能依赖或新的宿主能力时，需要检查相应真实路径；不能拿报告案例的结果替代。复杂场景的输入尚未明确时，说明缺少哪项具体事实，并继续其他不依赖它的已授权工作。

### 复杂应用：连续推进规则与实际安装

连续推进需求不只改变页面文字。它先改变主管在稳定条件下何时结束当前回合，随后牵动使用说明、静态合同、完整回归、安全检查、安装候选、真实安装状态、旧版归档和后续行为观察。按四个结论展开后，影响范围如下：

| 必须回答的结论 | 本次实际处理 |
|---|---|
| 变化后的用户结果 | 项目、目标、授权和停止条件稳定时，同一检查点内的相关本地步骤应连续完成；当前任务继续推进，不要求用户反复发送“继续”。 |
| 受影响能力与依赖 | 修改 Skill 主循环和日常用法，补充对应合同；冻结并扫描候选，再通过安装器完成 target/state 切换、旧版归档和 journal 核对。升级后的接续澄清只改使用说明和状态记录，没有再改 Skill 字节。 |
| 仍适用的旧证据 | 未改变的身份、权限、停止条件和其他合同继续由既有测试支持；完整回归用于检查没有发现相关退化。旧五次对话观察只覆盖旧规则和原情境，不能证明新增连续推进规则有效。 |
| 必须补验的部分 | 源码文字先做失败与通过对照，再执行相关合同、完整回归、静态安全检查和安装后核验；未来自然新任务还需确认加载新版并观察实际连续性。接续澄清没有改变活动 Skill，因此不需要重新安装。 |

这个例子说明，影响判断既不能只看修改文件，也不能把所有旧证据全部作废。真正改变的规则、安装状态和行为分别补证；未改变的安全合同按适用范围复用。当前安装完成不等于宿主重载或长期效果通过，未来观察也不阻止当前任务继续产出结果。

### 实际应用：维护对象从程序扩展到 Skill

本项目已将这一用户需求用于一次实际维护检查：核对主管源码、指定安装副本与发行材料中的 11 个文件，三者内容一致，内部文件链接有效；没有发现因文件版本不一致而需要修订或补装的依据。随后核对已有六份规则的原始验证材料，确认旧观察覆盖原来的对话情境，没有覆盖 writing-skills 及新的 Skill 修订过程。

因此，当时选择保留主管规则，补齐维护说明中的辅助依赖与证据适用范围。这个结果覆盖了“检查后有依据地不修改”的维护分支，也说明需求扩展会牵连使用入口、辅助能力、验证材料和生效方式。它是一次主线程实际应用，不是独立模型评测；在该检查点尚未执行规则修改、安装升级或数据迁移。

后续连续推进问题提供了另一条分支：先保留规则，等直接反馈与轨迹把问题定位为规则歧义后，再做最小修改、验证并安装。两次处理放在一起，说明 Skill 维护既包括有依据地不改，也包括证据充分后改到最小位置；第三方 Skill、新环境和长期行为仍需各自证据。

## 在检查点判断是否应该继续、调整或收束

普通本地修改采用短说明和相关检查；跨文件依赖或重要取舍才展开设计。每个有意义的检查点应说明本项解决了什么、所属方向还缺什么、整体接下来做哪项。额外模型、实际安装或发布的参与要求根据具体动作处理，不能从一次普通修复扩成默认授权。

若检查没有带来新信息，就停止重复；若原问题尚未改善，就回到原因和行动的对应关系。用户可以纠正目标或体验判断，主管应据此调整，并保留原失败的适用范围。整个方向是否完成，要看其可使用结果和必要验证，不看新增文档或检查数量。
