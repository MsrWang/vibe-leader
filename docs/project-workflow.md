# 日常项目用法：接续、检查与维护

在当前项目选择“中文跨项目研发主管”，然后按眼前的任务提出请求。下面四种请求沿用现有 Skill，帮助你说清要得到什么结果；项目资料和本次授权仍需现场核对。

本页随 3.0 有限范围交付，没有安装新的 Skill 规则。以下请求是可直接使用的表达方式；每个项目的实际结果仍需按当前任务核对，不能从一个案例推断所有情境都有效。

## 阶段做完后，继续整体项目

```text
使用 $vibe-project-lead-zh。核对当前项目的整体目标和最新有效决定。
说清这次完成了哪一部分、整体还剩什么，以及现在应继续哪一项。
在本任务已经授权的本地范围内，直接推进下一项必要工作，完成后检查实际效果。
条件没有变化时，连续推进到一个有意义的检查点，不需要我每隔几分钟重新说一次“继续”。
遇到需要我决定的重要取舍，请先给具体方案和理由。
```

主管应从已有计划、现场内容和对应结果中接续工作。一次修复、一次发布都只关闭各自范围；如果整体仍有未完成成果，应给出具体下一项。项目、目标、授权和停止条件稳定时，同一检查点内的调查、修改、关联核对和必要验证应连续完成，中间用简短进度说明保持你知情。资料确实不足时，说明缺少哪项决定或证据，而不是让你重新讲全部历史。

如果刚完成 Skill 更新，当前任务仍继续推进。以后在自然开启的新任务中核对新版是否被宿主重新加载，只是验证安装后行为的一种方式，不是当前工作的前置条件，也不要求为了测试中断正在进行的项目。当前任务可以继续产出结果；新任务只负责补充“新版已加载并产生预期行为”的独立证据。

## 检查代码质量，找值得处理的问题

```text
使用 $vibe-project-lead-zh。针对当前项目已经委托的目标检查代码质量。
先定位有证据的问题，解释影响、优先级和合适的改法。
属于本任务已授权范围的局部修复，请继续完成并检查直接关联处；
其余建议说明取舍。最后告诉我问题是否改善、哪些部分还没有验证。
```

有用的结果应解释“问题在哪里、为什么值得处理、修改后怎样证明有效”。代码更短、文件更小或测试更多，单独都不能证明质量提高。没有发现值得修改的问题时，应说明检查范围和依据。

## 维护当前项目负责的 Skill

```text
使用 $vibe-project-lead-zh。检查当前项目负责维护的 Skill 源码是否适合本次使用场景。
先分清问题来自规则内容、规则没有落实、来源或调用失效，还是配套程序和环境。
需要修改时，说明源码范围、验证方式及如何恢复；现有规则足够就说明如何正确使用。
准备候选与更新实际安装分别处理。
```

这项请求适用于负责该 Skill 源码的项目。模型曾参与编写，不代表当前任务可以修改其他项目或插件的安装文件。涉及职责、重要行为或权限的变化，需要明确解释其影响。[详细维护方法](maintenance-and-change.md)给出判断依据和案例。

## 需求变了，核对连带影响

```text
使用 $vibe-project-lead-zh。针对我刚提出的需求变化，核对受影响的能力和依赖。
说明代码、使用步骤和文档要怎样调整，哪些旧检查仍有效、哪些必须补验。
在本任务已授权的范围内继续实施，并在完成后核对遗漏和实际效果。
```

主管应把变更接到具体交付结果，解释验证选择。只有文案变化时，通常无需重做模型或安装检查；如果涉及数据、兼容或环境，就需要相应证据。影响尚不清楚的部分应保留为待核实。

## 怎样判断这次推进有用

看三个结果：当前最重要的缺口是否明确；采取了什么实际行动；行动后是否有对应变化。一次答复或一份新文档只能证明它本身已经形成，不能替代功能、环境或使用效果的检查。

已有成果和反馈应按适用范围复用。切换任务或项目时重新核对身份与本次工作范围；来源说明和旧记录不能替代新任务的授权。
