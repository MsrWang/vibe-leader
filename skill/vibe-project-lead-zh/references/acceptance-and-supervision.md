## 实施前提

在真实业务项目中，开始实现前确认并向用户说明：

- 真实目标、当前交付物与明确非目标；
- 用户能观察的验收标准；
- 当前绑定项目、HEAD、完整 dirty 指纹和既有用户修改；
- 允许修改的精确文件或行为范围；
- 将运行的测试、服务及可能生成的缓存、日志、数据库或其他状态；
- 当前实现步骤、停止条件和可执行回滚点；
- 适用项目规则、工程 Skill 和安全批准状态。

局部、低风险、边界清楚的改动可使用短计划；重大、跨文件或高影响改动先形成规格和详细计划。对新逻辑、修复和行为变化使用测试驱动：先确认能证明缺失行为的 RED，再写最小实现并取得 GREEN。不要删除有效测试、修改断言或降低规格来换取绿灯。

每个 worktree 同一时刻只有一个写入者。写入前重新绑定项目并确认允许文件；保留所有用户和其他来源的既有修改。测试、格式化和生成器也可能写状态，运行前把其副作用纳入范围。

## 证据等级

让证据负担与风险、寿命和后续依赖相称。只记录支持当前结论所需的字段，不为每条低风险命令创建报告，也不以字段数量代替证据质量。

### EV0

用于低风险、可快速重做的本地只读检查或局部 sanity check。最少记录：

- 方法或命令；
- 关键结果；
- `PASS`、`FAIL`、`UNKNOWN` 或 `NOT_APPLICABLE`；
- 与结论有关的警告。

EV0 可以只保留在当前任务。命令退出码为 0 仍要检查输出语义；部分输出或中断不得记为 PASS。

### EV1

用于项目身份、计划、实现检查点、测试套件、版本门、可靠性或后续步骤依赖的结论。最少记录：

- 需求、检查点或门禁 ID；
- 方法或命令；
- cwd；
- 与结论相关的 HEAD/diff 或适用环境；
- 退出码或等效结果；
- 关键摘要和明确状态；
- 警告、未覆盖范围与适用限制。

只有证据易漂移、属于生成产物或需要追溯时，再增加时间、证据路径或哈希。不要复制完整日志到聊天、状态账本和验收报告三处。

### EV2

用于 D-F 动作，以及认证、安全、部署、迁移、公开发布、生产或重大成本结论。必须包含全部 EV1 字段，并增加：

- 证据时间和目标环境；
- 审批 ID 与实际批准范围；
- 数据范围、凭据类别和调用范围；
- 预期副作用与实际副作用；
- 成功、失败或 unknown 判定；
- 可执行回滚方法和限制；
- 证据路径及必要哈希。

不得记录密钥、Token、Cookie、凭据值、生产数据或隐藏推理。审批格式和生命周期以安全 reference 为唯一详细真源。

## 证据新鲜度

在引用旧证据前，重新核对项目、logical/physical path、Git/worktree、HEAD、diff 或 `dirty_fingerprint`、环境、目标资源和证据时间。以下任一变化会使依赖它的测试、审查、批准或完成结论过期：

- 项目、worktree、分支、HEAD 或 dirty 指纹变化；
- 代码、配置、依赖、运行时、Skill locator 或测试合同变化；
- staging/production、账号、Provider、目标资源或数据范围变化；
- 证据超出其声明的有效时间或环境。

过期证据要重新验证或明确标为过期。不能用“之前通过过”“改动很小”或 memory 摘要维持 PASS。生成验收报告本身改变 diff 时，区分被验证的内容 HEAD 与仅报告文件产生的 diff。

## 两遍审查

每个有意义实现检查点按顺序完成两遍审查：

1. `需求符合性审查`：核对获批目标、范围、非目标和验收标准；检查漏项、越界、用户修改及未实现条件。
2. `质量与安全审查`：检查正确性、回归、路径、并发、权限、凭据、TOCTOU、回滚、unknown 和测试缺口。

先完成需求符合性，再进行质量与安全；一遍测试不能自动代表两遍审查。低风险任务可由 Codex 主线程分两遍完成。需要新鲜上下文、额外模型或子 Agent 时，先按主管工作流确定 S0/S1/S2，再进入安全批准门。

把审查结果绑定当前 HEAD 和 diff。代码、合同或运行时文件变化后，旧审查自动过期；先验证 finding，再以 RED-GREEN 做最小修正。不要因为 Agent 数量增加就宣称审查独立或有效。

## 固定结果分区

每个检查点和完成报告使用以下固定分区：

```text
已通过：有当前直接证据的项目
警告：不阻断当前结论但需要关注的项目
未验证：尚未检查或证据不足的项目
未知：中断、矛盾或无法判定的项目
用户验收：等待 / 通过 / 不通过
下一门禁：继续所需的条件或批准
```

warning 不并入 PASS，skipped 不冒充 NOT_APPLICABLE，技术验证不代替用户体验。`UNKNOWN` 既不是失败也不是成功；它阻断依赖该事实的高风险结论。只有获批设计明确让某项不适用且有直接依据时，才标记 `NOT_APPLICABLE`。

分区单位是同一对象、环境、时点上的具体判断，按以下规则使用当前证据：

- 观察或检查尚未开展、结果尚待用户提供时，列入“未验证”或“用户验收：等待”，说明缺少什么。仅因不知道未来是否通过，不能推导当前 `UNKNOWN`。
- 列入 `UNKNOWN` 时，写明哪个判断无法裁决、具体原因以及受影响的结论，例如检查中断或结果相互矛盾。若治理组件已返回 `UNKNOWN`，保留其状态与原因；首次没有比较基线等情形不能被“证据缺失一律未验证”覆盖。
- 同一具体判断的当前结果只分类一次；换措辞、换编号不会形成新的事实。一个功能的不同判断分别处理，例如计算已验证、导出格式未检查、同步结果因中断而未知。警告说明已知限制及影响，不制造相反的结果。
- 当前证据范围内没有无法裁决的判断时，UNKNOWN 栏显示“无”；有待办不等于有 UNKNOWN，UNKNOWN 为空也不等于目标已完成。

例如，“跨项目观察尚未开展”和“跨项目观察暂无结论”若指同一次待开展观察，应合为一项未验证，不能分别填入未验证与 UNKNOWN。输出前按事实含义核对，不能只比较字面字符串。

“已通过”只列当前证据实际证明的范围。“警告”必须说明为何不阻断当前结论。“未验证”和“未知”分别列出所缺证据与安全影响。用户验收必须来自用户实际观察或明确判断，不由主管代填。

## U0-U3 真人验收分级

完成技术验证后，使用 `ACCEPTANCE_DECISION_V1` 按用户可见性、业务影响、数据行为、外部副作用、可逆性、自动覆盖、环境差异、新颖程度和 UNKNOWN 判级；多个因素取最高级别：

| 级别 | 最低验收 |
|---|---|
| `U0` | 纯内部且行为/输出不变；替代测试和审查证据完整时可免真人验收 |
| `U1` | 低影响、可快速回滚；免除时记录理由、替代证据和用户覆盖权 |
| `U2` | 功能、业务逻辑、数据、兼容或工作流变化；必须引导用户做真实场景观察 |
| `U3` | 账号、敏感数据、费用、公开、生产、部署或不可逆动作；必须有动作前人工门、动作后观察和回滚验证 |

关键能力验证必须先完成；成果或关键能力为 `PARTIAL / MISSING / UNKNOWN` 时，不具备最终 UAT 前提。关键成果 UNKNOWN 至少 U2，外部、安全或不可逆事实 UNKNOWN 为 U3。用户可以提高验收等级，主管不得在没有新证据时降低。

只读敏感数据也必须判为 U3。U0/U1 免除必须留下替代证据。U2 的 `POST_ACTION_OBSERVATION` 和 U3 的 `PRE_ACTION_APPROVAL -> 外部动作结果 -> POST_ACTION_OBSERVATION -> ROLLBACK_VERIFICATION` 必须预先绑定 requirement，并由当前任务真实用户事件形成 `USER_EVENT_RECEIPT_V1`；缺失结果保持等待，主管不得代填或用 `recorded_by="USER"` 自证。U3 的前置 approval 必须发生在外部动作前，事后观察必须绑定动作结果，回滚验证必须在最终接受前完成。验收分类和结果始终是裁决证据，不产生 `write_authorized`。

主管不得替用户确认真人观察。进入 U2/U3 前先展示安全目标摘要、当前能力与环境、观察步骤、预期结果、失败停止点和已知限制，让用户能用真实工作流判断是否好用；Progress 可读性本身属于适用真人观察，技术测试或 reviewer 不能代填 PASS。

## 业务任务完成

只对用户本次业务目标报告完成。以下七项必须同时满足：

1. 目标、非目标和用户可观察的验收标准已经明确。
2. 必要的专业调查和推荐已经完成，并区分现场事实、来源事实、推断、建议和用户决定。
3. 适用实现、测试、两遍审查或交付证据绑定当前现场。
4. 警告、未验证、unknown、剩余风险和后续工作已经分开。
5. 需要用户观察或判断的部分已经完成用户验收。
6. 外部资源与实际批准一致，并存在停止或回滚方法。
7. 当前任务的恢复摘要已在有意义边界更新，并给出一个下一安全步骤。

任一适用项不满足时，报告实际进度和缺口，不用“基本完成”隐藏未决门。Skill 可用、测试通过、一次部署成功或 1.0 用户验收都不能关闭中文研发主管能力的总 Goal。

## 同一任务恢复

审批处理以 safety-gates.md 的“审批绑定与生命周期”为唯一详细真源；下列恢复检查与各版本验收均遵循同一口径，历史验收原件按其版本和时点保留。

上下文压缩、中断、关闭后重开或从摘要恢复时，把 memory、聊天摘要和旧状态当作定位提示，不当作项目或批准真源。按以下顺序恢复：

1. 重新确认中文主管仍适用于当前任务；必要时重新选择 Skill。
2. 把工具 cwd 设为目标项目，第一条 shell 命令独立执行 `pwd`。
3. 重新取得 logical/physical path、Git 根、git/common dir、worktree、分支、HEAD、dirty 摘要和完整指纹。
4. 读取项目原本存在且当前适用的规则、计划和直接证据。
5. 比较现场与恢复摘要；任何身份、代码、运行时或证据漂移先报告并使旧结论过期。
6. 若双捕获证明是 `stable same-task resume`，只保留未消费且仍匹配的本地包络；任务/项目/环境/目标/范围或控制锚点漂移时旧包络失效。已消费的一次性审批永不复用，E/F 外部审批永不恢复；不恢复已消费次数，副作用判断须重新核对当前证据。
7. 只选择一个当前仍安全的下一步骤继续。

用户不需要复述完整历史。优先从现场和当前任务可见状态重建；只有缺失信息会改变目标、风险、费用、不可逆后果或用户验收时，才询问一个必要问题。

## 新任务与项目切换

同一项目的新任务或 fork 仍要重新显式进入主管、独立执行 `pwd` 并从现场绑定。不要继承上游任务的项目状态、C-F 确认、HEAD、dirty 指纹、Agent 结果或完成结论。

切换项目必须开启新任务。当前任务返回 `STOP_PROJECT_SWITCH`，停止写入和审批消费；不同项目之间不得在同一任务内重新绑定。新任务重新选择主管、绑定项目并建立自己的目标、证据和批准，不继承上一个项目的 C-F 操作审批。Portfolio、memory 或跨项目摘要只能帮助定位，不能反向覆盖项目事实。

## 1.1 可靠性验收

1.1 的确定性技术 PASS 与用户体验验收保持分离，任何一方不能代替另一方。技术验收至少覆盖路径/执行面、Git 拓扑、两次完整捕获、freshness、route-local inventory、升级 journal/inspect/restore、七文件运行时和历史回归；每项绑定当前候选 HEAD、diff 和实际测试证据。

真人验收必须由用户在实际 Codex 界面观察 Windows/WSL 路径关系、中断后恢复和两个项目的新任务隔离。恢复后首条项目命令仍须独立 `pwd`，并按“同一任务恢复”检查未消费本地动作是否仍在有效范围；新任务不继承旧批准，已消费审批不复用，E/F 外部审批不恢复。freshness 为 `STALE`、`AMBIGUOUS` 或 `UNKNOWN` 时不得写入。截图只能证明界面来源，不能代替命令级项目身份。

真实升级另行记录安装前 manifest、旧版本归档、切换能力、阶段、gap、journal、安装后发现和可执行恢复。未执行或结果未知时明确标为 `NOT_PERFORMED` 或 `UNKNOWN`，不能并入 PASS。只有用户明确确认所有适用真人观察项，用户验收才可标为通过。

## 1.2 自适应委派验收

1.2 的结果必须分别记录 source freshness、return freshness 和 main-thread freshness，并把
结果绑定当前项目、worktree、HEAD、dirty fingerprint 与必要文件哈希。主线程先执行需求
符合性审查，再执行质量与安全审查；两遍都通过才可把结果送入主线程裁决。

确定性技术门至少包括 brief/result schema、预算与派生 ID、只读/Review/隔离写入、单写入者、
审批不继承、嵌套停止、一次消费、SOLO_FALLBACK、1.0/1.1 回归、py_compile 与 diff hygiene。
这些证据不等于 native Agent PASS、用户验收或 `write_authorized`。

用户实际观察至少覆盖：中文 brief 可理解；小任务保持 SOLO；委派收益可解释；过期结果拒绝；
隔离 worktree 和单写入者成立；外部审批不继承；冲突由主线程裁决；中断恢复后 freshness
重新捕获；原生能力缺失时安全回退。用户没有明确标记的场景保持等待，不代填 PASS。

## 1.0 版本退出门

1.0 只有同时满足以下条件才可进入 `USER_ACCEPTED`：

- 全部适用技术门为 `PASS`，不适用项都有获批设计和当前证据支持的 `NOT_APPLICABLE`；
- 适用行为评测没有未解释的 `FAIL` 或 `UNKNOWN`，评测仍绑定当前候选和工具边界；
- 九项实际界面用户验收均由用户明确标记通过；
- 禁用、旁路和可恢复回滚说明仍绑定当前候选、安装 manifest 和运行环境；
- 源码、安装副本、discovery、验收记录和当前候选哈希一致；
- 所有 warning、未验证、未知和过期高风险证据已经裁决，没有被分区展示掩盖；
- 用户对精确候选作出最终版本决定。

技术测试、行为评测、安装成功和用户体验分别记录，互不代替。任何适用项缺失都保持 `IN_PROGRESS`、`WAITING_GATE` 或 `NEEDS_REVISION`，不要降低门槛。1.0 进入 `USER_ACCEPTED` 后，只进入 1.1 的能力重新审计；总 Goal 保持 active。

## 原生恢复推翻条件

1.0 默认使用 Codex 原生 task、resume、fork、compact 和 memory 辅助恢复，不创建自定义 checkpoint。项目现场始终是事实权威。

若模拟测试或真实用户验收证明原生恢复出现以下任一情况，立即把 1.0 标为 `NEEDS_REVISION` 并重新比较 `CUSTOM_COMPONENT`：

- 无法可靠保留或重建必要项目事实；
- 无法识别 HEAD、dirty 指纹、项目身份或关键证据漂移；
- 恢复后错误继承外部批准、项目状态或另一个任务的结论；
- 迫使用户反复复述完整项目历史才能继续；
- 多次恢复不能稳定给出一个当前安全的下一步骤。

这个“原生恢复推翻条件”只重新打开设计比较，不授权静默创建 checkpoint、根 `AGENTS.md`、脚本、Custom Agent 或第二状态源。没有直接反证时保持原生恢复方案。
